# Architecture and conventions

Follow [UI direction](ui-direction.md) for visual and interaction contracts and [documentation direction](documentation-direction.md) for keeping guidance current.

## State and persistence

The CLI supplies no session credentials or account information to About. Theme loading retains its bundled name or resolved custom-file source separately from the JSON display name and saved configuration.

Packages separate cloud authentication/discovery, the MQTT transport, the monitor worker, normalized farm state, credential storage, configuration, and the terminal UI. The UI reducer alone mutates farm state. Transports communicate through messages and stop on context cancellation. Configuration, notice, and snooze persistence commands receive immutable snapshots and report completion through messages. Each store permits one write in flight; changes during that write coalesce into a complete latest snapshot after completion. Attempted, successfully saved, and failed revisions stay distinct, with no tick-driven retry of failed revisions. Normal quit waits up to five seconds, then requires an explicit exit or cancellation on failure/timeout; external cancellation reports unconfirmed saves after the terminal is restored.

`internal/notifications` owns the explicit synthetic macOS delivery probe used by `doctor --notify`. It locates `Bambu TUI Notify.app` beside the resolved CLI executable, registers that bundle using macOS Launch Services, and invokes its `Contents/MacOS/bambu-notify` with fixed test/sound arguments. Discovery does not search the current directory or fall back to AppleScript. The context-bound command has a 65-second deadline, allowing the helper's 60-second first-run permission/service wait, and is terminated on cancellation. The CLI owns output and separates accepted requests from confirmed banner/audio delivery; permission denial and helper timeout receive specific guidance. The probe reads no credentials or telemetry, changes no alert preferences, and keeps explicit tests independent from automatic delivery identities. Config exposes the same probe as a selectable Test Notification action, using the global sound preference captured at activation. An asynchronous command receives a child of the session context; the reducer tracks one pending test and its generation. Closing Config cancels the test, and stale results cannot replace newer state. The command never owns mutable farm/config state, and native acceptance remains distinct from presentation.

The `tools/macos-notify` Swift helper uses a universal app bundle included in macOS release archives and UserNotifications for branded delivery. Its app identity and icon belong to the bundle. `--test` submits a synthetic request with the explicit permission workflow; `--deliver` accepts bounded JSON on stdin and requires permission to have already been granted. Both submit immediate requests, and the helper exits after submission or its bounded permission/service wait. A launch without test arguments cannot submit a notification, preventing notification-click relaunches from generating another test. See [build, test, and cleanup instructions](contributing.md#macos-notification-helper).

## Local web monitoring

`internal/webserver` owns the optional embedded HTTP server and static assets. The CLI creates one session-owned server alongside the TUI, closes it on exit, and binds its cancellation to the dashboard context. The listener is always `tcp4` / `127.0.0.1:<port>`, with `[web_server].port` defaulting to 8080 and accepting 1–65535. Missing settings in older files receive the default; explicit invalid ports are rejected. A bind conflict leaves the service stopped with an occupied-port error; no fallback port is attempted. No headless lifecycle, LAN listener, account binding change, or additional monitor is introduced.

The reducer alone calls `SnapshotJSON` against normalized farm state, then publishes independent encoded bytes through an atomic snapshot. The explicit DTO excludes raw telemetry, serial identifiers, protocol job IDs, credentials, account information, storage paths, and backend errors. SHA-256 printer display identities and random 128-bit session occurrence targets preserve selection without exposing raw identifiers. The reducer retains targets only while their condition key, first-observed time, severity, and code still match, with text also identifying cloud and print-state replacements as in farm reconciliation; changing low-filament estimates and acknowledgement/dismissal/restoration do not rotate an ongoing target. Observed clears and replacement invalidate targets, including clear-and-recurrence at an identical timestamp. All browser clients read the same immutable bytes, never a farm pointer. `farm.Printer.TelemetryCurrent`, `ETACurrent`, `Connection`, and `State.Attention` retain shared freshness/estimate/intervention interpretation; UI helpers delegate to these methods. The web summary counts the whole farm and retains overlap between last-reported state, attention, and availability.

Settings serializes asynchronous enable/disable/port commands and coalesces rapid changes to the latest desired state and port. Applying a changed port while enabled closes the previous listener before binding the new one; failure leaves no listener. The running URL is reported only after a successful bind; failures persist without tick-driven retry. `r` in Web Server explicitly retries. Enabled and port participate independently in existing immutable configuration snapshots, field-level atomic merges, and shutdown save tracking. Settings closing leaves monitoring and HTTP active. Disabling closes the listener/connections and joins its Serve goroutine. Final CLI cleanup permanently closes the service, so a delayed command cannot reopen it after shutdown.

GET/HEAD serve the dashboard, its named assets, `/api/snapshot`, and `/api/session` (a random session CSRF token). The sole mutation route, `POST /api/dismiss`, requires exact Origin and Host, the CSRF header, exact `application/json`, a body at most 512 bytes, an opaque target, and an optional retry boolean. Unknown fields/trailing JSON fail. No permissive CORS, refresh, cloud proxy, or printer control is provided.

HTTP commands enter a bounded 16-slot channel and one reducer command waiter; handlers never receive farm pointers or write files. A buffered reply reports applied or rejected, independently of asynchronous durability. Full queues fail immediately; replies have a three-second deadline, and timeout/disconnection means outcome unknown. The reducer validates the current target and rejects commands during shutdown or disablement, then calls the existing farm dismissal. Duplicates do not advance review revisions. The ordinary panel/dialog/notification synchronization updates active and suspended views, attention, and delivery eligibility. Saves reuse account/region-scoped notice persistence, immutable snapshots, serialization/coalescing, failed-load protection, and bounded shutdown. Explicit browser retry is permitted only for an existing hidden occurrence and a failed idle writable store; it queues the latest complete snapshot without resetting saved decisions. Browser storage status describes the complete shared notice snapshot, not an isolated file per request. No durable success is reported before the existing persistence result succeeds. Future headless operation must host this same authoritative reducer command contract; no separate headless mode is added here. Exact Host and Origin checks, cross-site request rejection, no CORS, no-store telemetry responses, restrictive CSP, and HTTP time/header limits constrain local browser access. There is no authentication; other local users/programs can read display data, obtain the token, and submit local notice decisions. The token is cross-site request protection, not local-client authentication. Static files require no CDN, Node build, or internet access. Known model names map to a fixed allowlist of content-versioned generated printer sprites; unknown names retain the generic browser illustration. Sprite routes cache only immutable artwork with private browser caching, while snapshots remain no-store. JavaScript escapes external strings before HTML insertion and validates reported color swatches. Visible pages poll without overlapping requests; hidden pages pause polling. Failed requests and delayed snapshots label retained readings last-known, separately from printer/cloud connectivity.

## Notification identity foundation

`farm.NotificationSnapshot` returns an independent snapshot of fresh, connected printer observations. It reuses verified `Attention` classification and local reviews; offline, stale, missing, null, and malformed families cannot establish absence. Condition identity excludes printer names, changing messages, percentages, and local acknowledgement/dismissal state. A confirmed family-specific clear retires its occurrence; a later recurrence or changed severity/code/print state gets a new opaque occurrence ID. Existing notice lifetimes and review persistence remain independent.

Notification job metadata belongs to the telemetry layer. It tracks normalized `task_id`/`subtask_id` and explicitly reported job state after an accepted report. An identity-only delta invalidates that metadata's state; a changed task cannot inherit the previous task's subtask ID or terminal state. Completion candidates require observed activity followed by reported `FINISH` for the same non-placeholder identity, including persisted activity from an earlier session. Startup `FINISH`, missing/zero IDs, failed/canceled jobs, progress, and ETA cannot generate completion. Completed/baselined tuples remain tombstoned: if firmware reuses an identical tuple for another run, completion is conservatively suppressed. Partial identity changes can also suppress completion until matching activity/state is observed. These are local safety policies, not a hardware-verified uniqueness guarantee; see [protocol evidence](../reference/protocol-sources.md#notification-job-identity).

`internal/notification_state` provides the versioned account/region ledger under `bambu-tui/notifications/` in the OS configuration directory. Filenames hash the account/region; stored printer/condition/job keys are length-delimited SHA-256 digests, and occurrence IDs are random 128-bit values. No tokens, raw job IDs, names, messages, or full telemetry are stored. New directories use 0700 and files/lock files use 0600. A nonblocking OS file lock serializes transactions, including across processes; each transaction reloads before changing state. Atomic replacement commits changed snapshots. Unknown/corrupt/oversized files, lock contention, and storage failures return errors without permitting delivery or overwriting unreadable state. Completed-job tombstones are retained; the 4,096-entry/2 MiB limits fail closed rather than evicting deduplication history. There is no automatic retry of delivery attempts or retention purge. Paused delivery can explicitly recheck the existing ledger without discarding identities.

`Observe` persists lifecycle changes and returns stable unreserved candidates. The delivery worker rechecks current preferences, snoozes, reviews, and eligibility before calling `Reserve`. `Reserve`/`ReserveBatch` persist attempts before the OS call; grouped reservations commit atomically and skip already-claimed members. Only a successful new reservation permits delivery. `RecordResult` records native acceptance or failure separately. A reservation surviving a crash has an unknown outcome and remains deduplicated. This chooses at-most-once attempts: a crash between reservation and submission can lose a notification; exact-once visual delivery across the filesystem and macOS is not claimed. Failed attempts also require a later explicit retry policy rather than retrying every report. Quiet-hours consumption uses a reserved then `quiet_suppressed` result, with the same fail-closed crash boundary and no replay. Older readers reject this additional attempt value safely.

Ledger operations perform synchronous filesystem I/O on a serialized live-session worker using immutable farm snapshots. The reducer alone reads live farm/review/snooze state and submits snapshots with resolved category, sound, and completion policies. Desktop delivery is independently opt-in globally/per printer. The worker preserves every queued lifecycle frame, but delivers only from current matching state/policy. Co-reported eligible intervention candidates on the same printer share one OS submission; each member retains its own occurrence, reservation, and result. With the optional burst window enabled, still-current candidates across reports, printers, and completions share one submission while retaining individual ledger identities. A policy/identity change affecting a member cancels the in-flight group conservatively. Session accepted/failed counters count OS submissions, not included notices. It checks eligibility before and after reservation, and newer snooze/review/identity/connection changes cancel an in-flight helper. A bounded 256-frame queue disables delivery on overflow rather than blocking the reducer or dropping lifecycle transitions. Suppression counts track newly recorded per-incident decision transitions with bounded in-memory coalescing; they are not telemetry report counts.

Normal monitoring prepares an idle client on local macOS so Config can enable delivery without restarting. Ledger observation and file creation begin only after desktop delivery is opted in. Once started, observation continues with muted policies to retain occurrence lifetimes. Demo uses a temporary ledger and labels notifications Demo; doctor remains repeatable and bypasses the ledger. The native sender sends bounded plain-text printer-title/body/sound JSON through stdin, uses a ten-second command deadline, and does not request permission. Native acceptance, failed submission, and ambiguous interruption remain distinct. UI footers preserve error indications and access to complete status details; the alert dialog displays effective settings and session counters. Normal shutdown pauses delivery and waits on worker/persistence activity for up to five seconds; canceling shutdown resumes the worker. Final exit cancels native work and bounds the worker join to five seconds; unconfirmed work is reported after terminal restoration, and no later OS submission may start. Already accepted notifications may still be presented by macOS. Quiet hours and timed grouping are described below.

`Store.ObserveActivity` returns the same unreserved candidates as `Observe`, plus runtime-only suppression metadata for reviewed/non-actionable conditions, prior accepted/failed/reserved attempts, and completion baselines/missing identity. The persistent document schema and reservation policy are unchanged. `NotificationCondition.Reviewed` is derived from local acknowledgement/dismissal and does not establish physical resolution. Eligibility and identity remain distinct.

The notification worker owns a session-only 100-record activity ring, bounded names/subjects, allowlisted outcome/reason codes, timestamps, repeat counts, and shared request numbers for grouped members. It retains the last diagnostic decision for up to 4,096 occurrence IDs to prevent repeated identical decisions from refilling the ring after row eviction. Changed reasons produce new rows; matching retained decisions update their time/count without repeated toasts. Older coalescing identities expire FIFO; diagnostic retention never changes persistent deduplication. `Status` returns an independent activity slice under the worker lock. No raw backend error text, credentials, raw telemetry, or protocol job IDs enter history, and no activity metadata is persisted. Native acceptance/failure is recorded before saving its result, so a later ledger write failure adds Paused without hiding the actual OS outcome.

`Store.AcquireOwner` holds a separate account/region `.owner.lock` with nonblocking OS flock and private permissions. It stores only a random 128-bit continuity token, rotated and synced under each acquired lease, with no PID or account metadata. The file is never unlinked/replaced; the lease releases on descriptor/process exit. A reacquiring observer compares the previous token with its last lease token before replaying queued observations, detecting even owners that acquired and exited without visible contention. Malformed tokens fail closed without being overwritten. Only the owner performs worker lifecycle transactions and automatic delivery. Standbys keep monitoring but do not read/write the ledger. Their one-second poll requests a new UI Submit even if values are unchanged; it cannot acquire ownership or send from a cached snapshot. A takeover skips obsolete queued frames before ownership. The established owner continues recording all queued lifecycle transitions and checking latest eligibility before delivery. On desktop opt-out it retains ownership until those queued observations drain, preserving confirmed clears and recurrences while the latest muted policy prevents delivery; a failure still releases ownership after in-flight work returns. Muted `ObserveOnly` frames cannot send; they temporarily acquire ownership to observe lifetimes when no active owner holds it, preserving queued observations and releasing after draining. A changed lease token or encountered competing owner breaks observation continuity: subsequent acquisition must begin with the newest snapshot, rather than applying obsolete clears over the other owner’s state. Explicit recovery also requires a fresh snapshot. New and retained leases update the public ownership role from each processed frame, including promotion of a temporary observer lease when desktop delivery is re-enabled; role changes advance status and activity history.

A paused worker remains alive under its session context, cancels its current sender, and releases ownership after that call returns. If queue overflow pauses an idle owner between processing calls, the serialized loop releases ownership while skipping queued frames; release does not depend on processing another frame. Stop/parent cancellation still joins the worker and releases its descriptor before Done closes. `Retry` is a nonblocking reducer control permitted only when paused/standby work is idle; it drains old queue entries and gates processing until a fresh Submit. It preserves the ledger, activity, and counters, and clears the error only for a new validation attempt. Corrupt/full state fails closed again, and prior accepted/failed/reserved attempts remain deduplicated. This is recovery of the worker, not replay of an OS request. File I/O stays on the serialized worker. The CLI never recreates account/region stores when a pending region preference is edited.

The dashboard's `N` route owns the activity dialog. It follows newest decisions initially; navigation pins selection by activity sequence through incoming reports, with oldest-retained fallback after eviction and Home restoring follow mode. The view keeps per-incident subject/channel/outcome/reason and group metadata visible at the supported minimum size. Empty/unsupported/opt-out states do not start the ledger or request permission. Config and doctor probes remain independent. Explicit worker recovery never retries consumed attempts; quiet-hour scheduling remains independent from recovery. The activity view supports only worker rechecks, not identity reset.

The separate Config dialog owns General, Alerts, Printers, and Web Server sections, the validated percentage input, and per-printer reset confirmation. All alert defaults/overrides and the low-filament threshold apply through the reducer immediately; threshold edits call the existing farm reconciliation. A region edit updates only the configuration snapshot, keeping the active cloud connection and account/region stores unchanged until restart/login. Discovered and saved absent printer IDs form the target list; the chosen ID stays pinned through discovery updates. Reset affects only overrides.

Serialized configuration commands receive deep value snapshots, including independently owned override maps and optional booleans. The CLI's writer closure owns the last successfully saved snapshot, reloads valid TOML, and merges differences into the current file via `config.SaveChanges`. Untouched external values survive, edited fields win, and failures never advance the saved baseline. Writes remain private/atomic, normalize TOML/remove comments, coalesce newer revisions, participate in shutdown, and retry only after a new edit or explicit Config retry. Successful saves are silent; failures remain red. Tests and permission requests remain separate explicit actions.

Farm view preferences use stable named `view.filter`/`view.sort` configuration values. Loading normalizes missing/unknown/non-string choices independently to All/Name; startup restoration does not create a write revision. The reducer detects effective filter/sort changes, including explicit navigation that reveals a hidden printer, and advances the shared config revision. F/S and dashboard 0 therefore reuse serialized snapshots, merging, failure/retry, and shutdown handling rather than creating another store. Scope follows the config path across accounts/regions and demo. No telemetry or selected identity is persisted; live ordering and identity-based selection remain owned by the farm view. Each view field merges independently from other settings.

## Palette and feedback

The UI owns an immutable style bundle per Model, constructed from the value-only `Palette` in `internal/ui/palette.go`. `DefaultPalette` reads the embedded `internal/ui/themes/default.json` definition for all app-owned default colors; there is no mutable global theme or style state. `WithPalette` replaces the bundle and rebuilds cached viewport content for the dashboard, active dialog, and suspended routes, detaching their cache owners without commands, automatic attention, timer changes, or behavioral mutations. Renderer helpers receive the model's styles; validated filament colors remain telemetry.

Bundled themes use one `embed.FS` with `themes/*.json`. Filenames supply the selectable names, and CLI help and generic bundle verification discover that inventory rather than maintaining per-theme declarations or switches. Adding a shipped theme requires its complete JSON and a build to embed it. Custom theme files are read from disk at each startup by the existing binary, independently of that compiled inventory; no registration or rebuild is required. Explicit file paths bypass bundled-name lookup.

The CLI loads a bounded version 1 JSON theme before authentication or monitor startup for dashboard/login commands. `theme_file` paths resolve against the active TOML directory; a launch-only `--theme` takes precedence without modifying that configuration snapshot. CLI choices select embedded `default`/`gruvbox-dark`/`hotdog`/`c64`/`ibm3270`/`deskmate` themes or a JSON path relative to the working directory; parsing rejects unknown/duplicate keys, unsupported versions, and malformed colors while filling omitted roles from the embedded default. Configuration owns only the `theme_file` path; it never imports UI types. The reducer retains that path in value snapshots, and the existing merge writer preserves unrelated external changes. Selection and file edits apply on restart. A final viewport compositor applies default body foreground/background after nested ANSI resets and fills blank cells without changing explicit selection/footer or telemetry colors. See [palette roles and contrast assumptions](ui-direction.md#palette-and-message-emphasis).

Transient feedback carries its own `feedbackKind`, set together with its text/timestamp. The notification worker publishes `Status.LastKind` as presentation-neutral runtime metadata, set at ownership/recovery/suppression/outcome creation under its existing lock. The UI maps it to palette roles without parsing message text. This adds no ledger schema, identity, delivery, retention, or retry-policy change. Config tests retain their own kind independently of pending/failure flags and existing dim/expiry timing; source-specific persistent errors still control their own lifetime.

## Dialogs

Dialog focus is owned by `dialogState` in `internal/ui/dialogs.go`. Its route catalog supplies keyboard handling, rendering, synchronization, and payload cleanup for each dialog; open/close transitions use that owner rather than pointer priority. Snooze controls opened from attention explicitly suspend and return to that prompt. Status / Feedback (`Ctrl+E`) can suspend any ordinary dialog, including snooze controls over attention. The bounded owner chain retains up to two suspended routes and synchronizes all three while status owns input; closing status restores the prior chain without running parent cleanup. Reset confirmations stay inside their owning decisions/Config dialog, preserving selection, input, and scroll. Help and status use independent viewports. Clear-history and clear-notices capture event IDs at opening, preserving later arrivals. Persistent feedback reads source-specific errors; late export/browser failures clear only after a successful operation. Background notification messages do not replace an active local toast. Automatic attention waits until the owner releases focus, including during persistence shutdown.

## Telemetry

Within `internal/farm`, `telemetry.go` owns report decoding, job-field invalidation, and flexible delta merging; `normalize.go` interprets the merged snapshot. `telemetry_presence.go` records condition-family and per-slot knowledge, distinguishing omitted data from explicit empty collections or reported unknown estimates. Review lifetime decisions consume that knowledge in `reviews.go`, while `state.go` and `conditions.go` handle lifecycle, history, and reconciliation. `Printer.Raw` remains the merged input for telemetry interpretation and allowlisted diagnostic snapshots; diagnostics still sanitize and re-normalize their own independent snapshot rather than serializing the live printer or its internal knowledge.

Telemetry envelopes and retained print snapshots are bounded independently: 2 MiB of key/string bytes, 8,192 JSON values, depth 32 (root depth zero), and 256 entries per object or array. Wire bodies also have a 2 MiB limit before JSON decoding. Unknown fields are retained within these budgets. Reports merge into an independent candidate and are rejected in full if any limit is exceeded; rejection leaves firmware, freshness, normalized state, history, and local notice decisions unchanged. Accepted partial reports still preserve omitted fields, and explicit empty collections clear them. These bounds limit cumulative retention and recursive/identity-merge work; they do not establish physical fault resolution.

## Monitor workers

The monitor resets reconnect backoff after two minutes following successful subscription, initial refresh, and the connected event. Short failures retain exponential delays from one to sixty seconds, plus up to 25% jitter; failed discovery/dial/bootstrap time does not establish a healthy session. Periodic discovery runs in one cancellable worker, and one outbound worker serializes subscriptions, refresh batches, and pings. Pending refreshes coalesce, new subscriptions are retained, and due pings take the next write slot. Device discovery events precede subscribing to added printers; received reports retain their read order.

Initial subscription/refresh stays ahead of connected/report events and must complete within ten seconds. With the event consumer draining its channel, slow discovery does not block report forwarding or the 25-second keepalive schedule. Refresh writes also leave report forwarding responsive, subject to MQTT's shared packet mutex for QoS acknowledgements. Each whole outbound batch (including waiting for that mutex) has a ten-second deadline: a due ping starts after at most the current batch, or the stalled connection closes within that bound. With the default intervals, a continuing connection starts a ping within about 35 seconds of the previous scheduled ping; a ping that itself stalls is also terminated after ten seconds, below the 60-second MQTT keepalive. These are operation deadlines rather than real-time scheduler guarantees. On cancellation, the monitor cancels discovery, closes the transport, and joins its reader/discovery/writer workers before returning. API implementations must honor context cancellation, and transport `Close` must release pending reads and writes. Slow-operation tests inject poll/ping ticks and block operations behind channels; the transport packet-framing test also exercises concurrent QoS acknowledgements and partial writes.

## Shared types and storage

Monitor messages use `monitor.EventKind` and the `EventDevices`, `EventConnection`, `EventReport`, and `EventProblem` constants. The private UI reducer returns a concrete `Model`; its public `Update` method adapts that result to Bubble Tea. Notice and snooze stores share `internal/atomicfile.Replace` for same-directory temporary-file creation, sync/close, rename, and cleanup. Each store still owns encoding, loading/validation, account paths, and contextual errors. Files remain private (0600), newly created directories use 0700, and existing directory permissions are unchanged. UI persistence commands retain ordering, failed-load protections, and the shutdown policy described above.

## Code conventions

Meaningful domain and protocol values belong to their owning packages. Reuse farm state, severity, category, condition-key, and inventory constants across consumers. Keep unrelated policies separate even when their numeric values match (for example ETA age, firmware age, and active print telemetry age). Use structs for records with distinct fields, including notice line spans, table columns, regional endpoints, request bodies, and fault classification rules. Flexible telemetry maps preserve unknown keys and omitted-field semantics.

Declarative catalogues and schemas intentionally retain literal code-to-description entries, allowlist keys/enumerations, regular expressions, serialization tags, palette definitions, and fixed command arguments: each definition states the value's meaning at its point of declaration. Ordinary first-element access, loop/count arithmetic, standard numeric bases/word sizes, and one-off display prose also stay inline. Synthetic demo payloads and literal test wire/persistence fixtures remain independent examples of the external formats; do not rewrite fixtures to derive expected wire values from implementation constants. Name new behavioral thresholds or positional meanings rather than adding another unexplained literal.

## Quiet scheduling and delivery bounds

Global `alerts.quiet_hours` and `burst_window_seconds` are file-configured value fields, validated on load and preserved by Config's merge writer. The reducer evaluates quiet wall-clock policy using its clock on every notification snapshot. The schedule uses a named timezone, start-inclusive/end-exclusive minutes, start-day overnight weekdays, and identical policy on repeated DST minutes. It affects only automatic desktop banners/sound, without urgent exceptions or modal/review changes. Otherwise eligible quiet occurrences are durably consumed; there is no exit summary or backlog replay. Queued quiet frames retain consumption even when a newer frame has exited the schedule.

The serialized worker observes every lifecycle frame before considering delivery. A fixed optional burst deadline begins at the first eligible event; later reports do not extend it. Current unreserved candidates are reconstructed from the ledger and latest snapshot, rather than retained in another identity queue. The worker's existing one-second poll requests fresh reducer submissions while waiting for a window/rate slot; it cannot deliver cached telemetry itself. At most twelve automatic OS attempts start per rolling minute in one worker, using a bounded twelve-timestamp session list; failures/unknown outcomes consume slots and never retry. Restart/takeover resets the rate window, while persistent at-most-once identities remain. All members are revalidated and reserved individually/atomically as before; grouping changes neither reviews nor condition lifetimes. Explicit synthetic probes bypass these automatic policies.
