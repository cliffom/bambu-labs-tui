## State and persistence

The CLI supplies no session credentials or account information to About. Theme loading retains its bundled name or resolved custom-file source separately from the JSON display name and saved configuration.

Packages separate cloud authentication/discovery, the MQTT transport, the monitor worker, normalized farm state, credential storage, configuration, and the terminal UI. `internal/session.Session` owns farm mutations, reconciliation, local notice decisions, occurrence targets, and persistence revisions. The TUI embeds it by value and invokes it only on the Bubble Tea reducer loop; `serve` and `serve --demo` host it on a serial loop that also supports terminal-free operation. The serve loop optionally owns a compact terminal presenter, updated from typed monitor events and session persistence status on that same loop. It samples terminal dimensions on refresh, keeps a bounded typed diagnostic list, applies default semantic palette styles, reads independent HTTP client-ledger snapshots, and rate-limits rendering to one second. Noninteractive hosts emit changed-state plain logs. The presenter creates no input reader, raw mode, signal handler, worker, or independent mutable session; deferred cleanup restores its alternate screen and cursor even on output errors. Each process has one state owner. Exported farm/snooze fields are read views for rendering and notification snapshots; production adapters must use session methods for mutations. Transports communicate through messages and stop on context cancellation.

`internal/accountstore` enforces one cloud host per account/region in the same OS configuration directory, covering both notices and snoozes. Both CLI hosts acquire a nonblocking exclusive OS file lock before loading saved notices/snoozes or starting a monitor, HTTP listener, terminal UI, or notification worker. Contention exits with fixed stop-and-retry guidance; lock creation/access failure also stops startup, without a session-only fallback. Demo bypasses account ownership and real-account stores. Different config files retain the same account scope. Hashed account/region lock filenames live under private `bambu-tui/sessions/` (0700 directories, 0600 empty files). Lock files are never unlinked or atomically replaced. The OS releases locks on exit/crash; all cooperating hosts must use v0.3.6 or newer. Mixed older writers and manual file edits during monitoring are unsupported.

Ownership spans startup loads, acknowledgement, hide/restore, mark-unreviewed, reset, confirmed resolution/recurrence, snooze/resume, and expired/removed-printer cleanup. Complete snapshot replacement remains safe because a second host cannot load or mutate an independent stale session. Hosts drain persistence under ownership using the existing bounded shutdown. Closing the store immediately rejects delayed jobs; already-entered writes retain the lock until they complete, without making Close wait for stuck I/O. Thus a timed-out callback cannot overwrite a successor's snapshot after ownership transfers. Raw notice/snooze stores are serialization primitives; production hosts must load/save through the owning account store. `Session.WithAccountPersistence` loads/restores both stores and attaches their writers through one shared policy. Fixed sanitized diagnostics and independent failed-load write protection are identical across terminal and foreground hosts; hosts retain lease acquisition, interaction, and bounded shutdown. Running hosts do not observe external edits; prompt and desktop delivery eligibility use their loaded state and serial local transitions. New hosts load the latest committed snapshots after acquisition. No cross-process live synchronization is claimed. Notification ledger transactions, delivery ownership, reservation identities, and worker shutdown remain separate and unchanged.

Session persistence jobs receive immutable snapshots and return typed results; the TUI adapts those jobs/results to commands/messages. Notice/snooze callbacks and write trackers stay private to the session, with copied status for the host. Configuration jobs clone the complete host-supplied configuration, including TUI view choices. Each host must deliver completions back on its serial loop and request the next jobs after state changes or results. Jobs must never read live session state. Each store permits one write in flight; changes during that write coalesce into a complete latest snapshot after completion. Attempted, successfully saved, and failed revisions stay distinct, with no tick-driven retry of failed revisions. `Session.RetryPersistence` queues only selected failed writable stores that have no queued/running attempt, without advancing domain revisions. The TUI uses it for `r` in Status / Feedback; browser retry uses it only for notices after validating a current hidden occurrence. Duplicate queued/in-flight retries are ignored; capture uses the latest complete snapshot, and newer edits coalesce after completion. Each notice/snooze job carries a separate attempt generation as well as its revision, rejecting delayed completions even when an explicit retry uses the same revision. Shared save-state accessors report saving/saved/failed/session-only, including queued retries. Failed-load write protection, prompt suppression, occurrence identities, snooze deadlines, and notification attempts are unchanged. Normal terminal quit waits up to five seconds, then requires an explicit exit or cancellation on failure/timeout; external cancellation reports unconfirmed saves after the terminal is restored.

`internal/notifications` owns the explicit synthetic macOS delivery probe used by `doctor --notify`. It locates `Bambu TUI Notify.app` beside the resolved CLI executable, registers that bundle using macOS Launch Services, and invokes its `Contents/MacOS/bambu-notify` with fixed test/sound arguments. Discovery does not search the current directory or fall back to AppleScript. The context-bound command has a 65-second deadline, allowing the helper's 60-second first-run permission/service wait, and is terminated on cancellation. The CLI owns output and separates accepted requests from confirmed banner/audio delivery; permission denial and helper timeout receive specific guidance. The probe reads no credentials or telemetry, changes no alert preferences, and keeps explicit tests independent from automatic delivery identities. Config exposes the same probe as a selectable Test Notification action, using the global sound preference captured at activation. An asynchronous command receives a child of the session context; the reducer tracks one pending test and its generation. Closing Config cancels the test, and stale results cannot replace newer state. The command never owns mutable farm/config state, and native acceptance remains distinct from presentation.

The `tools/macos-notify` Swift helper uses a universal app bundle included in macOS release archives and UserNotifications for branded delivery. Its app identity and icon belong to the bundle. `--test` submits a synthetic request with the explicit permission workflow; `--deliver` accepts bounded JSON on stdin and requires permission to have already been granted. Both submit immediate requests, and the helper exits after submission or its bounded permission/service wait. A launch without test arguments cannot submit a notification, preventing notification-click relaunches from generating another test. See [build, test, and cleanup instructions](contributing.md#macos-notification-helper).

## Local web monitoring

`internal/webserver` owns the optional embedded HTTP server and static assets. The CLI creates one session-owned server alongside the TUI, closes it on exit, and binds its cancellation to the dashboard context. The listener is always `tcp4` / `127.0.0.1:<port>`, with `[web_server].port` defaulting to 8080 and accepting 1–65535. Missing settings in older files receive the default; explicit invalid ports are rejected. A bind conflict leaves the service stopped with an occupied-port error; no fallback port is attempted. The foreground demo lifecycle is described below. Neither adapter introduces a LAN listener or additional monitor per browser tab.

`internal/webserver` also owns a mutex-protected session-only HTTP client ledger. `ConnContext` associates requests with a socket; `ConnState` follows socket closes, and the first request supplies a bounded, terminal-sanitized User-Agent. IPs come from the socket, never forwarding headers. Requests group sockets by the displayed IP/User-Agent pair, creating one client lifetime across parallel or replaced connections. Sockets without requests do not create entries. Last-socket closure starts a five-second grace period; matching activity cancels expiry, while snapshot/request processing retires expired groups. Listener shutdown retires all groups immediately, ignoring late close callbacks. Snapshot reads copy the 32-event ring and active/omission counts for both terminal presenters. At most 128 sockets and 128 groups are tracked; omitted details are counted and the active count covers tracked groups. Callbacks never touch farm/session state, write files, or publish client metadata to HTTP DTOs. A client group is a best-effort display identity, not an authenticated person/tab; the ledger is not persisted.

The reducer calls `Session.Publish`, which refreshes the session occurrence registry and publishes an independent `session.DisplayState` value with copied optional scalars, slices, and nested collections. The session imports no HTTP adapter and owns no JSON schema/encoding. `webserver.EncodeDisplay` maps that transport-independent contract to its explicit wire allowlist, selects artwork, and publishes encoded bytes through an atomic snapshot. `DecisionCommand` / `DecisionResult` carry local policy without HTTP request/reply channels; each host adapter converts its bounded web command/reply around the serial session call. The explicit DTO excludes raw telemetry, serial identifiers, protocol job IDs, credentials, account information, storage paths, and backend errors. SHA-256 printer display identities and random 128-bit session occurrence targets preserve selection without exposing raw identifiers. The session retains targets only while their condition key, first-observed time, severity, and code still match, with text also identifying cloud and print-state replacements through `farm.SameCondition` / `SameOccurrence`, shared with reconciliation and restored reviews; changing low-filament estimates and acknowledgement/dismissal/restoration do not rotate an ongoing target. Every accepted telemetry/reconciliation transition refreshes an initialized target registry, so observed clears and replacements invalidate targets even without publication between reports, including clear-and-recurrence at an identical timestamp. All browser clients read the same immutable bytes, never a farm pointer. `farm.Printer.TelemetryCurrent`, `ETACurrent`, `Connection`, and `State.Attention` retain shared freshness/estimate/intervention interpretation; UI helpers delegate to these methods. The session display adds an `IdleFinished` eligibility value only for current online printers explicitly reporting `IDLE` or `FINISH`, using the shared freshness windows; the HTTP allowlist exposes it as `idle_finished`. The browser additionally gates this view/count on a connected, non-delayed feed without changing notice decisions or claiming physical readiness. The web summary counts the whole farm and retains overlap between last-reported state, attention, and availability.

Settings serializes asynchronous enable/disable/port commands and coalesces rapid changes to the latest desired state and port. Applying a changed port while enabled closes the previous listener before binding the new one; failure leaves no listener. The running URL is reported only after a successful bind; failures persist without tick-driven retry. `r` in Web Server explicitly retries. Enabled and port participate independently in existing immutable configuration snapshots, field-level atomic merges, and shutdown save tracking. Settings closing leaves monitoring and HTTP active. Disabling closes the listener/connections and joins its Serve goroutine. Final CLI cleanup permanently closes the service, so a delayed command cannot reopen it after shutdown.

GET/HEAD serve the dashboard, its named assets, `/api/snapshot`, and `/api/session` (a random session CSRF token). The local notice mutation route, `POST /api/dismiss`, requires exact Origin and Host, the CSRF header, exact `application/json`, a body at most 512 bytes, an opaque target, and an optional retry boolean. Unknown fields/trailing JSON fail. No permissive CORS, refresh, cloud proxy, or printer control is provided.

HTTP commands enter a bounded 16-slot channel and one reducer command waiter; handlers never receive farm pointers or write files. A buffered reply reports applied or rejected, independently of asynchronous durability. Full queues fail immediately; replies have a three-second deadline, and timeout/disconnection means outcome unknown. The TUI supplies shutdown/enablement gates to `Session.ApplyWebCommand`; the session validates the current target and rejects commands during shutdown or disablement, then applies the local dismissal. Duplicates do not advance review revisions. The ordinary panel/dialog/notification synchronization updates active and suspended views, attention, and delivery eligibility. Saves reuse account/region-scoped notice persistence, immutable snapshots, serialization/coalescing, failed-load protection, and bounded shutdown. Explicit browser retry is permitted only for an existing hidden occurrence and a failed idle writable store; it queues the latest complete snapshot without resetting saved decisions. Browser storage status describes the complete shared notice snapshot, not an isolated file per request. No durable success is reported before the existing persistence result succeeds. The foreground demo adapter hosts this same contract as described below. Dialog routing, selection, rendering, prompt rearming, status/toast formatting, notification-worker integration, HTTP lifecycle commands, and interactive shutdown confirmations remain TUI responsibilities; HTTP request protections remain in `internal/webserver`. Exact Host and Origin checks, cross-site request rejection, no CORS, no-store telemetry responses, restrictive CSP, and HTTP time/header limits constrain local browser access. There is no authentication; other local users/programs can read display data, obtain the token, and submit local notice decisions. The token is cross-site request protection, not local-client authentication. Static files require no CDN, Node build, or internet access. Known model names map to a fixed allowlist of content-versioned generated printer sprites; unknown names retain the generic browser illustration. Sprite routes cache only immutable artwork with private browser caching, while snapshots remain no-store. JavaScript escapes external strings before HTML insertion and validates reported color swatches. Visible pages poll without overlapping requests; hidden pages pause polling unless browser notifications are enabled, in which case polling continues best-effort. Failed requests and delayed snapshots label retained readings last-known, separately from printer/cloud connectivity. The display snapshot includes the explicit device online flag so browser activity grouping remains independent of freshness and cloud-disconnected labels.

### Browser notification worker

`Session.Publish` also builds an independent `notifications.Input` from `farm.NotificationSnapshot`, current categories/completion/sound settings, reviews, snoozes, and quiet hours. Browser policy ignores native desktop enablement. Both production hosts submit after every accepted event/reconciliation and policy update, including when the TUI listener is disabled, preserving clear/recur transitions between browser polls. No live farm pointers leave the serial owner. Normalized internal worker snapshots may contain protocol identity for Go lifecycle tracking; HTTP responses contain only random occurrence IDs, opaque printer display IDs, display names, fixed allowlisted prose, and a sound boolean.

`internal/webserver` owns a separate serialized browser worker with a bounded 256-entry observation/request queue. It reuses `notification_state.Store.ObserveActivity` for family-specific unknown/clear/recur semantics and confirmed job lifetimes. Production storage uses the account/region native ledger path with a `.browser` suffix, separate transactions/locks and attempt identities; account-host ownership prevents competing lifecycle observers. Demo uses temporary private storage removed only after the worker joins. Disk I/O stays outside the session reducer and HTTP handlers. Overflow/storage failures pause delivery until repair/restart, with fixed public errors. Session submissions never wait on disk; the worker verifies that queued observations are drained and rechecks the submission generation after reservation, dropping conservatively if newer input arrived during I/O.

`POST /api/notifications` uses the same exact Host/Origin, CSRF token, content type, 512-byte limit, unknown/trailing-field rejection, and three-second reply bounds as notice commands. Its body contains only `baseline` and `after` cursor fields. A baseline returns the current event sequence without claiming. Other requests reserve eligible, unexpired candidates newer than the cursor before returning display-only events. All connected browsers share at-most-once reservations. Failed/unknown submissions and lost responses remain reserved without retry. Quiet/muted/reviewed/snoozed events are consumed; pending events expire after fifteen seconds, retaining first-seen time across unknown snapshots. Up to twelve attempts per rolling minute are reserved per running worker, with no deferred backlog or native burst grouping. State/memory remain bounded; retired identities never reset the durable ledger.

`notifications.js` owns origin-local opt-in, permission checks, synthetic tests, storage-event synchronization, and page-created `Notification` objects. Permission is requested only by Enable/Test clicks. Enable, reload, reconnect, and polling gaps over ten seconds establish baselines; enabled hidden pages continue best-effort polling. Clicks focus the page and inspect the matching printer without review mutation; close has no decision handler. Constructor/async errors and unconfirmed presentation remain visible. No service worker, push subscription, or remote access is added. Closing the server cancels the worker; CLI cleanup joins it for up to five seconds and leaves demo storage intact if filesystem work is still blocked. See [user policy](../user/alerts.md#browser-system-notifications).

### Foreground server host

`cmd/bambu-tui/serve.go` hosts `internal/session` on one serial select loop for `serve` and `serve --demo`. It consumes one cloud or synthetic monitor, one-second reconciliation ticks, browser commands, and immutable persistence completions. It publishes allowlisted snapshots after transitions; HTTP handlers never read mutable state. Persistence jobs run outside the owner and return through a bounded result queue, allowing one write per store and coalescing newer revisions. Failed revisions are not retried automatically.

The CLI binds before printing its URL, forces HTTP on without modifying saved enablement, and uses the configured port without fallback. `Server.ListeningDone` exposes the current listener lifetime independently of parent cancellation, so unexpected HTTP termination fails the process even without another telemetry event. Browser tabs do not own the process. On SIGINT/SIGTERM the host gates decisions, closes HTTP, and drains accepted writes/coalesced revisions for up to five seconds. Failed or timed-out saves return a nonzero exit with unconfirmed-save guidance; cleanup cancels the monitor and bounds its join to five seconds. A stuck store callback cannot be interrupted, but cannot block process exit beyond the drain deadline.

Demo does not attach real-account persistence, config saving, credentials, or a native notification worker. Local decisions remain session-only and saved preferences remain untouched. The loop's drain contract is exercised with injected stores; production demo has no durable decision jobs. Terminal themes and interactive login are unused. Cloud-backed `serve` uses cancellable, 15-second-bounded native credential lookup with no interactive login fallback, the existing cloud discovery/MQTT runner, and account/region-scoped notice/snooze stores. Failed loads disable writes to preserve saved data; notice retry uses the same session command contract. `monitor.Event.StopReason` conveys terminal authentication rejection independently of human-readable connection text. Individual telemetry decoder rejections are recoverable: the owner skips publication for that event and continues with accepted state, without advancing telemetry timestamps, condition lifetimes, or local decisions. Normal reconciliation ticks still age retained data. A fixed warning goes to the cloud host diagnostics writer once per server session, bounding output without payloads, identifiers, or raw errors. Transient failures reconnect; rejected authentication or unexpected stream closure fails the headless host, while parent cancellation exits normally after draining. The TUI retains its existing authentication notice behavior. Neither foreground server creates a native notification worker or changes saved configuration; localhost access protections and display-data boundaries are identical to the TUI server.

### TUI server inspection

The shared dialog router owns Server Status (`W`), with Config optionally suspended beneath it and Status / Feedback above it. All three synchronize through the existing reducer; closing inspection runs no Config cleanup and does not change listener settings. The normal reducer reads immutable `Server.Status` and copied `Server.Clients` observations before synchronizing dialogs, so asynchronous lifecycle and persistence results appear immediately. The existing one-second dashboard tick refreshes uptime and disconnect expiry; inspection starts no monitor, listener, timer loop, or terminal reader. `Status.Started` records only the current successful listener binding and clears on stop/failure. The Model records its separate session start and up to eight fixed, sanitized monitor/rejection diagnostics. Existing owners still control all lifecycle and storage mutations.

Config and inspection share HTTP lifecycle presentation; the modal and foreground presenter share `ClientEvent.DisplayLine`. Tracking limits, grouping, sanitization, disconnect grace, and history remain owned by the webserver ledger. Neither status timestamps nor client metadata enter display DTOs or persistence. The modal uses an independent themed viewport, preserves offset where content permits, and leaves its cache untouched during below-minimum fallback. Dashboard focus and Config selection/edit/confirmation state remain with their suspended owners.

## Notification identity foundation

`farm.NotificationSnapshot` returns an independent snapshot of fresh, connected printer observations. It reuses verified `Attention` classification and local reviews; offline, stale, missing, null, and malformed families cannot establish absence. Condition identity excludes printer names, changing messages, percentages, and local acknowledgement/dismissal state. A confirmed family-specific clear retires its occurrence; a later recurrence or changed severity/code/print state gets a new opaque occurrence ID. Existing notice lifetimes and review persistence remain independent.

Notification job metadata belongs to the telemetry layer. It tracks normalized `task_id`/`subtask_id` and explicitly reported job state after an accepted report. An identity-only delta invalidates that metadata's state; a changed task cannot inherit the previous task's subtask ID or terminal state. Completion candidates require observed activity followed by reported `FINISH` for the same non-placeholder identity, including persisted activity from an earlier session. Startup `FINISH`, missing/zero IDs, failed/canceled jobs, progress, and ETA cannot generate completion. Completed/baselined tuples remain tombstoned: if firmware reuses an identical tuple for another run, completion is conservatively suppressed. Partial identity changes can also suppress completion until matching activity/state is observed. These are local safety policies, not a hardware-verified uniqueness guarantee; see [protocol evidence](../reference/protocol-sources.md#notification-job-identity).

`internal/notification_state` provides the versioned account/region ledger under `bambu-tui/notifications/` in the OS configuration directory. Filenames hash the account/region; stored printer/condition/job keys are length-delimited SHA-256 digests, and occurrence IDs are random 128-bit values. No tokens, raw job IDs, names, messages, or full telemetry are stored. New directories use 0700 and files/lock files use 0600. A nonblocking OS file lock serializes transactions, including across processes; each transaction reloads before changing state. Atomic replacement commits changed snapshots. Unknown/corrupt/oversized files, lock contention, and storage failures return errors without permitting delivery or overwriting unreadable state. The version-2 live document remains bounded at 4,096 entries / 2 MiB. Retired job digests move to the exact archive described below; unresolved incidents are never discarded for space. There is no automatic retry of delivery attempts or identity expiry. Paused delivery can explicitly recheck the existing ledger without discarding identities.

### Exact job history and maintenance

Each channel uses `<ledger>.jobs/format` plus sorted binary digest buckets with an explicit format header and SHA-256 content checksum. Buckets contain at most 4,096 length-delimited identity digests (32 bytes each); full buckets retain their entries and overflow into longer two-hex-digit prefixes, bounding each read/replacement at approximately 128 KiB. This trades gradual disk growth for exact indefinite replay suppression rather than trading away the at-most-once guarantee. There is no background archive scan, expiry, probabilistic match, or claim of bounded total disk usage. Missing individual buckets caused by external deletion cannot be distinguished from never-created buckets; complete backups and no manual deletion are part of the storage contract.

Transactions retain the existing nonblocking ledger lock across archive access and live-document changes. Valid v1 state is upgraded and committed as v2 with its archive marker before the first archival write, so older binaries fail closed even after interrupted migration. For each observation, known fresh successor identities retire previous jobs for that printer; closed and consumed terminal jobs may retire while absent. Unknown/stale/disconnected observations never supersede unfinished jobs. Every retired digest is atomically committed with directory durability before its live record can be removed; batched retirements replace each touched bucket once. An interrupted/failed transaction may conservatively consume jobs already archived, but cannot forget their identity. Reservation checks consult the archive even if an interrupted compaction left a duplicate live record. Recommitting a visible duplicate repairs ambiguous prior directory-sync outcomes before live deletion. Bad checksums, unsupported headers, missing archive markers, invalid documents and storage errors fail closed without overwriting unreadable data.

`compact-notifications --consume-unfinished` acquires the existing account lease before touching either channel; each `Store.CompactJobs` also takes delivery ownership and the transaction lock. This explicit offline decision archives all jobs, including unfinished jobs for absent printers. Their later completions are forfeited, while new tuples can notify. Incidents, reviews, snoozes and prior attempt deduplication remain intact. Native and browser compactions commit independently and are idempotent. A ledger full of unresolved incidents still needs confirmed telemetry clears; unreadable or unsupported state must be restored/repaired, not reset. Workers expose live capacity and warn at 80%; this is independent from delivery recovery and physical fault resolution. See [user recovery and backup policy](../user/alerts.md#notification-history-and-capacity).

`Observe` persists lifecycle changes and returns stable unreserved candidates. The delivery worker rechecks current preferences, snoozes, reviews, and eligibility before calling `Reserve`. `Reserve`/`ReserveBatch` persist attempts before the OS call; grouped reservations commit atomically and skip already-claimed members. Only a successful new reservation permits delivery. `RecordResult` records native acceptance or failure separately. A reservation surviving a crash has an unknown outcome and remains deduplicated. This chooses at-most-once attempts: a crash between reservation and submission can lose a notification; exact-once visual delivery across the filesystem and macOS is not claimed. Failed attempts also require a later explicit retry policy rather than retrying every report. Quiet-hours consumption uses a reserved then `quiet_suppressed` result, with the same fail-closed crash boundary and no replay. Older readers reject this additional attempt value safely.

Ledger operations perform synchronous filesystem I/O on a serialized live-session worker using immutable farm snapshots. The reducer alone reads live farm/review/snooze state and submits snapshots with resolved category, sound, and completion policies. Desktop delivery is independently opt-in globally/per printer. The worker preserves every queued lifecycle frame, but delivers only from current matching state/policy. Co-reported eligible intervention candidates on the same printer share one OS submission; each member retains its own occurrence, reservation, and result. With the optional burst window enabled, still-current candidates across reports, printers, and completions share one submission while retaining individual ledger identities. A policy/identity change affecting a member cancels the in-flight group conservatively. Session accepted/failed counters count OS submissions, not included notices. It checks eligibility before and after reservation, and newer snooze/review/identity/connection changes cancel an in-flight helper. A bounded 256-frame queue disables delivery on overflow rather than blocking the reducer or dropping lifecycle transitions. Suppression counts track newly recorded per-incident decision transitions with bounded in-memory coalescing; they are not telemetry report counts.

Normal monitoring prepares an idle client on local macOS so Config can enable delivery without restarting. Ledger observation and file creation begin only after desktop delivery is opted in. Once started, observation continues with muted policies to retain occurrence lifetimes. Demo uses a temporary ledger and labels notifications Demo; doctor remains repeatable and bypasses the ledger. The native sender sends bounded plain-text printer-title/body/sound JSON through stdin, uses a ten-second command deadline, and does not request permission. Native acceptance, failed submission, and ambiguous interruption remain distinct. UI footers preserve error indications and access to complete status details; the alert dialog displays effective settings and session counters. Normal shutdown pauses delivery and waits on worker/persistence activity for up to five seconds; canceling shutdown resumes the worker. Final exit cancels native work and bounds the worker join to five seconds; unconfirmed work is reported after terminal restoration, and no later OS submission may start. Already accepted notifications may still be presented by macOS. Quiet hours and timed grouping are described below.

`Store.ObserveActivity` returns the same unreserved candidates as `Observe`, plus runtime-only suppression metadata for reviewed/non-actionable conditions, prior accepted/failed/reserved attempts, and completion baselines/missing identity. The observation also returns value-only live capacity; archive retention uses the version-2 schema above. Reservation policy remains at-most-once. `NotificationCondition.Reviewed` is derived from local acknowledgement/dismissal and does not establish physical resolution. Eligibility and identity remain distinct.

The notification worker owns a session-only 100-record activity ring, bounded names/subjects, allowlisted outcome/reason codes, timestamps, repeat counts, and shared request numbers for grouped members. It retains the last diagnostic decision for up to 4,096 occurrence IDs to prevent repeated identical decisions from refilling the ring after row eviction. Changed reasons produce new rows; matching retained decisions update their time/count without repeated toasts. Older coalescing identities expire FIFO; diagnostic retention never changes persistent deduplication. `Status` returns an independent activity slice under the worker lock. No raw backend error text, credentials, raw telemetry, or protocol job IDs enter history, and no activity metadata is persisted. Native acceptance/failure is recorded before saving its result, so a later ledger write failure adds Paused without hiding the actual OS outcome.

`Store.AcquireOwner` holds a separate account/region `.owner.lock` with nonblocking OS flock and private permissions. It stores only a random 128-bit continuity token, rotated and synced under each acquired lease, with no PID or account metadata. The file is never unlinked/replaced; the lease releases on descriptor/process exit. A reacquiring observer compares the previous token with its last lease token before replaying queued observations, detecting even owners that acquired and exited without visible contention. Malformed tokens fail closed without being overwritten. Only the owner performs worker lifecycle transactions and automatic delivery. Standbys keep monitoring but do not read/write the ledger. Their one-second poll requests a new UI Submit even if values are unchanged; it cannot acquire ownership or send from a cached snapshot. A takeover skips obsolete queued frames before ownership. The established owner continues recording all queued lifecycle transitions and checking latest eligibility before delivery. On desktop opt-out it retains ownership until those queued observations drain, preserving confirmed clears and recurrences while the latest muted policy prevents delivery; a failure still releases ownership after in-flight work returns. Muted `ObserveOnly` frames cannot send; they temporarily acquire ownership to observe lifetimes when no active owner holds it, preserving queued observations and releasing after draining. A changed lease token or encountered competing owner breaks observation continuity: subsequent acquisition must begin with the newest snapshot, rather than applying obsolete clears over the other owner’s state. Explicit recovery also requires a fresh snapshot. New and retained leases update the public ownership role from each processed frame, including promotion of a temporary observer lease when desktop delivery is re-enabled; role changes advance status and activity history.

A paused worker remains alive under its session context, cancels its current sender, and releases ownership after that call returns. If queue overflow pauses an idle owner between processing calls, the serialized loop releases ownership while skipping queued frames; release does not depend on processing another frame. Stop/parent cancellation still joins the worker and releases its descriptor before Done closes. `Retry` is a nonblocking reducer control permitted only when paused/standby work is idle; it drains old queue entries and gates processing until a fresh Submit. It preserves the ledger, activity, and counters, and clears the error only for a new validation attempt. Corrupt/full state fails closed again, and prior accepted/failed/reserved attempts remain deduplicated. This is recovery of the worker, not replay of an OS request. File I/O stays on the serialized worker. The CLI never recreates account/region stores when a pending region preference is edited.

The dashboard's `N` route owns the activity dialog. It follows newest decisions initially; navigation pins selection by activity sequence through incoming reports, with oldest-retained fallback after eviction and Home restoring follow mode. The view keeps per-incident subject/channel/outcome/reason and group metadata visible at the supported minimum size. Empty/unsupported/opt-out states do not start the ledger or request permission. Config and doctor probes remain independent. Explicit worker recovery never retries consumed attempts; quiet-hour scheduling remains independent from recovery. The activity view supports only worker rechecks, not identity reset.

The separate Config dialog owns General, Alerts, Printers, and Web Server sections, the validated percentage input, and per-printer reset confirmation. All alert defaults/overrides and the low-filament threshold apply through the reducer immediately; threshold edits call the existing farm reconciliation. A region edit updates only the configuration snapshot, keeping the active cloud connection and account/region stores unchanged until restart/login. Discovered and saved absent printer IDs form the target list; the chosen ID stays pinned through discovery updates. Reset affects only overrides.

Serialized configuration commands receive deep value snapshots, including independently owned override maps and optional booleans. The CLI's writer closure owns the last successfully saved snapshot, reloads valid TOML, and merges differences into the current file via `config.SaveChanges`. Untouched external values survive, edited fields win, and failures never advance the saved baseline. Writes remain private/atomic, normalize TOML/remove comments, coalesce newer revisions, participate in shutdown, and retry only after a new edit or explicit Config retry. Successful saves are silent; failures remain red. Tests and permission requests remain separate explicit actions.

Farm view preferences use stable named `view.filter`/`view.sort` configuration values. Loading normalizes missing/unknown/non-string choices independently to All/Name; startup restoration does not create a write revision. The reducer detects effective filter/sort changes, including explicit navigation that reveals a hidden printer, and advances the shared config revision. F/S and dashboard 0 therefore reuse serialized snapshots, merging, failure/retry, and shutdown handling rather than creating another store. Scope follows the config path across accounts/regions and demo. No telemetry or selected identity is persisted; live ordering and identity-based selection remain owned by the farm view. Each view field merges independently from other settings.

## Palette and feedback

The UI owns an immutable style bundle per Model, constructed from the value-only `Palette` in `internal/ui/palette.go`. `DefaultPalette` reads the embedded `internal/ui/themes/default.json` definition for all app-owned default colors; there is no mutable global theme or style state. `WithPalette` replaces the bundle and rebuilds cached viewport content for the dashboard, active dialog, and suspended routes, detaching their cache owners without commands, automatic attention, timer changes, or behavioral mutations. Renderer helpers receive the model's styles; validated filament colors remain telemetry.

Bundled themes use one `embed.FS` with `themes/*.json`. Filenames supply the selectable names, and CLI help and generic bundle verification discover that inventory rather than maintaining per-theme declarations or switches. Adding a shipped theme requires its complete JSON and a build to embed it. Custom theme files are read from disk at each startup by the existing binary, independently of that compiled inventory; no registration or rebuild is required. Explicit file paths bypass bundled-name lookup.

The CLI loads a bounded version 1 JSON theme before authentication or monitor startup for dashboard/login commands. `theme_file` paths resolve against the active TOML directory; a launch-only `--theme` takes precedence without modifying that configuration snapshot. CLI choices select embedded `default`/`gruvbox-dark`/`hotdog`/`c64`/`ibm3270`/`deskmate` themes or a JSON path relative to the working directory; parsing rejects unknown/duplicate keys, unsupported versions, and malformed colors while filling omitted roles from the embedded default. Configuration owns only the `theme_file` path; it never imports UI types. The reducer retains that path in value snapshots, and the existing merge writer preserves unrelated external changes. Selection and file edits apply on restart. A final viewport compositor applies default body foreground/background after nested ANSI resets and fills blank cells without changing explicit selection/footer or telemetry colors. See [palette roles and contrast assumptions](ui-direction.md#palette-and-message-emphasis).

Transient feedback carries its own `feedbackKind`, set together with its text/timestamp. The notification worker publishes `Status.LastKind` as presentation-neutral runtime metadata, set at ownership/recovery/suppression/outcome creation under its existing lock. The UI maps it to palette roles without parsing message text. This adds no ledger schema, identity, delivery, retention, or retry-policy change. Config tests retain their own kind independently of pending/failure flags and existing dim/expiry timing; source-specific persistent errors still control their own lifetime.

## Dialogs

Dialog focus is owned by `dialogState` in `internal/ui/dialogs.go`. Its route catalog supplies keyboard handling, rendering, synchronization, and payload cleanup for each dialog; open/close transitions use that owner rather than pointer priority. Snooze controls opened from attention explicitly suspend and return to that prompt. Status / Feedback (`Ctrl+E`) can suspend any ordinary dialog, including snooze controls over attention. The bounded owner chain retains up to two suspended routes and synchronizes all three while status owns input; closing status restores the prior chain without running parent cleanup. Reset confirmations stay inside their owning decisions/Config dialog, preserving selection, input, and scroll. Help and status use independent viewports. Clear-history and clear-notices capture event IDs at opening, preserving later arrivals. Persistent feedback reads source-specific errors; late export/browser failures clear only after a successful operation. Background notification messages do not replace an active local toast. Automatic attention waits until the owner releases focus, including during persistence shutdown.

## Telemetry

Within `internal/farm`, `telemetry.go` owns report decoding, job-field invalidation, and flexible delta merging; `normalize.go` interprets the merged snapshot. `telemetry_presence.go` records condition-family and per-slot knowledge, distinguishing omitted data from explicit empty collections or reported unknown estimates. Review lifetime decisions consume that knowledge in `reviews.go`, while `state.go` and `conditions.go` handle lifecycle, history, and reconciliation. `Printer.Raw` remains the merged input for telemetry interpretation and allowlisted diagnostic snapshots; diagnostics still sanitize and re-normalize their own independent snapshot rather than serializing the live printer or its internal knowledge.

Job metadata invalidation happens before merging a changed known task/subtask identity or an idle/finished/failed transition into slicing, preparing, or running. Each boundary clears both previous task/subtask associations before merging incoming fields. IDs omitted at that boundary remain unknown for the new job, so their delayed arrival fills missing identity without resetting newly received names, estimates, or state. A changed known identity also invalidates the old print state, so identity/name reports arriving before the state cannot inherit the previous job's completion or trigger a second metadata reset when running arrives. Omitted metadata within the same job remains available; normalization prefers the reported subtask name over the G-code path. Notification job evidence retains its separate explicit-state tracking.

Telemetry boundary detection and notification evidence share protocol job-ID normalization. Numeric/string zero, empty, and invalid IDs are unknown rather than confirmed identities; transitions to or from those placeholders do not independently establish a display metadata boundary. Raw reports retain the supplied values, while comparison uses normalized IDs on both sides.

Telemetry envelopes and retained print snapshots are bounded independently: 2 MiB of key/string bytes, 8,192 JSON values, depth 32 (root depth zero), and 256 entries per object or array. Wire bodies also have a 2 MiB limit before JSON decoding. Unknown fields are retained within these budgets. Reports merge into an independent candidate and are rejected in full if any limit is exceeded; rejection leaves firmware, freshness, normalized state, history, and local notice decisions unchanged. Accepted partial reports still preserve omitted fields, and explicit empty collections clear them. These bounds limit cumulative retention and recursive/identity-merge work; they do not establish physical fault resolution.

## Monitor workers

The monitor resets reconnect backoff after two minutes following successful subscription, initial refresh, and the connected event. Short failures retain exponential delays from one to sixty seconds, plus up to 25% jitter; failed discovery/dial/bootstrap time does not establish a healthy session. Periodic discovery runs in one cancellable worker, and one outbound worker serializes subscriptions, refresh batches, and pings. Pending refreshes coalesce, new subscriptions are retained, and due pings take the next write slot. Device discovery events precede subscribing to added printers; received reports retain their read order.

Initial subscription/refresh stays ahead of connected/report events and must complete within ten seconds. With the event consumer draining its channel, slow discovery does not block report forwarding or the 25-second keepalive schedule. Refresh writes also leave report forwarding responsive, subject to MQTT's shared packet mutex for QoS acknowledgements. Each whole outbound batch (including waiting for that mutex) has a ten-second deadline: a due ping starts after at most the current batch, or the stalled connection closes within that bound. With the default intervals, a continuing connection starts a ping within about 35 seconds of the previous scheduled ping; a ping that itself stalls is also terminated after ten seconds, below the 60-second MQTT keepalive. These are operation deadlines rather than real-time scheduler guarantees. On cancellation, the monitor cancels discovery, closes the transport, and joins its reader/discovery/writer workers before returning. API implementations must honor context cancellation, and transport `Close` must release pending reads and writes. Slow-operation tests inject poll/ping ticks and block operations behind channels; the transport packet-framing test also exercises concurrent QoS acknowledgements and partial writes.

## Shared types and storage

Monitor messages use `monitor.EventKind` and the `EventDevices`, `EventConnection`, `EventReport`, and `EventProblem` constants. The private UI reducer returns a concrete `Model`; its public `Update` method adapts that result to Bubble Tea. Configuration, notice, snooze, and notification stores share `internal/atomicfile.Replace` for same-directory temporary-file creation, file sync/close, rename, directory commits, and cleanup. Each store still owns encoding, loading/validation, account paths, and contextual errors. Files remain private (0600), newly created directories use 0700, and existing directory permissions are unchanged. Shared session jobs retain ordering and failed-load protections; the TUI preserves the shutdown policy described above.

After rename, replacement syncs and closes the destination directory and every ancestor, deepest first through the filesystem root, before returning success. Existing ancestors are included on every attempt: lock setup may have just created them, or an earlier failed attempt may have left unsynced parent entries visible. No process-local creation cache can bypass a failed commit on retry. This adds directory sync work to each changed snapshot; unchanged notification observations still avoid writes. Directory-open/sync/close errors propagate, including on filesystems that do not support directory sync. A post-rename error leaves a complete new file visible with unconfirmed durability; it does not authorize native sending or browser event return. Notification consumers fail closed and honor visible reservations on recovery. This is the supported macOS/Linux sync contract, conditional on the filesystem/storage honoring those operations; it does not claim hardware power-loss validation or stronger drive-cache guarantees than the OS sync APIs provide.

## Code conventions

Meaningful domain and protocol values belong to their owning packages. Reuse farm state, severity, category, condition-key, and inventory constants across consumers. Keep unrelated policies separate even when their numeric values match (for example ETA age, firmware age, and active print telemetry age). Use structs for records with distinct fields, including notice line spans, table columns, regional endpoints, request bodies, and fault classification rules. Flexible telemetry maps preserve unknown keys and omitted-field semantics.

Declarative catalogues and schemas intentionally retain literal code-to-description entries, allowlist keys/enumerations, regular expressions, serialization tags, palette definitions, and fixed command arguments: each definition states the value's meaning at its point of declaration. Ordinary first-element access, loop/count arithmetic, standard numeric bases/word sizes, and one-off display prose also stay inline. Synthetic demo payloads and literal test wire/persistence fixtures remain independent examples of the external formats; do not rewrite fixtures to derive expected wire values from implementation constants. Name new behavioral thresholds or positional meanings rather than adding another unexplained literal.

## Quiet scheduling and delivery bounds

Global `alerts.quiet_hours` and `burst_window_seconds` are file-configured value fields, validated on load and preserved by Config's merge writer. The reducer evaluates quiet wall-clock policy using its clock on every notification snapshot. The schedule uses a named timezone, start-inclusive/end-exclusive minutes, start-day overnight weekdays, and identical policy on repeated DST minutes. It affects only automatic desktop banners/sound, without urgent exceptions or modal/review changes. Otherwise eligible quiet occurrences are durably consumed; there is no exit summary or backlog replay. Queued quiet frames retain consumption even when a newer frame has exited the schedule.

The serialized worker observes every lifecycle frame before considering delivery. A fixed optional burst deadline begins at the first eligible event; later reports do not extend it. Current unreserved candidates are reconstructed from the ledger and latest snapshot, rather than retained in another identity queue. The worker's existing one-second poll requests fresh reducer submissions while waiting for a window/rate slot; it cannot deliver cached telemetry itself. At most twelve automatic OS attempts start per rolling minute in one worker, using a bounded twelve-timestamp session list; failures/unknown outcomes consume slots and never retry. Restart/takeover resets the rate window, while persistent at-most-once identities remain. All members are revalidated and reserved individually/atomically as before; grouping changes neither reviews nor condition lifetimes. Explicit synthetic probes bypass these automatic policies.
