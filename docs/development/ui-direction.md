# UI direction

[Documentation index](../README.md) · [Architecture](architecture.md) · [Documentation direction](documentation-direction.md)

## Product and visual direction

Keep the interface a compact, keyboard-operated farm monitor. Operators should be able to find unavailable or troubled printers, understand the reported condition, and inspect details without losing their place as telemetry arrives. Preserve read-only behavior unless the user explicitly changes that product scope.

Extend the existing dashboard hierarchy: version/connection header, farm summary, printer list, printer details, and notices. Put detailed inspection or local configuration in the existing dialog system. Build shared styles from the semantic palette in `internal/ui/palette.go`; keep layout and timing policies in `internal/ui/values.go`, table widths in `internal/ui/layout.go`, and version helpers in `internal/ui/version.go`. Preserve semantic roles and a visible selected-row background. The default theme uses green accent, muted secondary text, amber warnings/offline rows, and red errors; user themes may change these colors. Introduce a new style or layout policy only for a clear operator need, and explain it in the PR.

Color supplements text. Preserve readable state labels, fault codes, focus/selection markers, and unknown/last-known qualifiers when color is unavailable. Treat printer names and other external strings as untrusted terminal text; use existing sanitization and ANSI-aware width/wrapping helpers. Avoid decorative content that consumes space needed for monitoring or navigation.

Use a full-width themed background (slate in the default theme) for the bottom dashboard, action-needed, and full-screen notice footer, with a one-column horizontal inset. Use bold, bright dashboard hotkeys with secondary labels and keep dashboard warnings amber; preserve the footer's single-row height and readable controls without color. Keep hints specific to the focused panel and enabled actions. Essential close/return and confirmation controls remain visible during feedback. Summarize overlapping failures with a count and `^E status` (`Ctrl+E`); show full messages and recovery guidance in the scrollable Status / Feedback view. Ordinary transient feedback lasts eight seconds and does not replace persistent errors. Background notification activity must not replace a local action's feedback interval.

## Palette and message emphasis

`internal/ui/themes/default.json` is the authoritative default color definition, embedded in the binary and exposed by `DefaultPalette()`. `Palette` defines the semantic role inventory and its exact JSON names. `newStyles` builds an immutable style bundle owned by each Model; views use that bundle rather than package-global styles or inline color literals. Start from a copy of the default palette when overriding roles. `WithPalette` rebuilds dashboard and active/suspended dialog caches without scheduling work, opening attention, changing input/confirmation/selection/scroll, or resetting feedback timers. It detaches dialog cache owners so recoloring a model value does not change the original value's rendering. Version 1 JSON files override any subset of the default roles through the startup-only `theme_file` configuration setting or launch-only `--theme` override. Bundled `default`, `gruvbox-dark`, `hotdog`, `c64`, `ibm3270`, and `deskmate` choices require no external files. Bundled names are discovered from a wildcard-embedded JSON directory; user files load at runtime through their paths and require no Go registration or rebuild. See [custom themes](../user/usage.md#custom-themes) for the format, path resolution, validation, and examples.

| Palette roles | Default RGB | Use |
| --- | --- | --- |
| `Background` | `null` | Inherit terminal background by default; custom RGB paints every body cell, margin, and blank row |
| `Text`, `Info`, `Hotkey` | `#E4E9F0` | Primary values, fresh body information, header hotkeys |
| `SecondaryText`, `MutedText` | `#929BA8` | Labels/metadata versus unavailable/de-emphasized content; separate roles despite equal defaults |
| `Accent`, `Success`, `Focus`, `Border` | `#A3E4BB` | Headings, confirmed local success/OS acceptance, focused sections, dialog border; independently overridable roles |
| `Warning`, `Error` | `#F4BA72`, `#FF8087` | Warning/error content in the body |
| `SelectedText`, `SelectedBackground` | `#D9F5E4`, `#263B36` | Selected rows, including offline printer labels and activity outcomes; take precedence over warning/outcome colors and retain the explicit marker |
| `FooterBackground` | `#3A4652` | Continuous slate surface, including every separator and padding cell |
| `FooterText`, `FooterSeparator` | `#B8C2CE` | Hint labels and separators; separate roles |
| `FooterInfo`, `FooterHotkey` | `#E4E9F0` | Bright, bold fresh information and controls; separate roles |
| `FooterSuccess`, `FooterWarning`, `FooterError` | `#A3E4BB`, `#F4BA72`, `#FF9AA1` | Bold success, warning, and error feedback on slate |
| `FooterMuted` | `#929BA8` | Deliberately dimmed Config results, without bold |

Fresh informational feedback must be prominent, including “This TUI owns desktop delivery,” standby/observer/recovery coordination, and refresh requests. Confirmed local notice edits and successful local exports/browser commands use success. Notification acceptance uses success but retains its unconfirmed-presentation wording. Malformed/monitor/reconnect problems use warning; explicit operation failures use error. Persistent storage/delivery problems keep the existing amber dashboard warning/red dialog error convention. Meaning is assigned at message creation through `feedbackKind` and notification `MessageKind`, never inferred by matching prose. Meaning, persistence, and display lifetime remain independent: ordinary feedback lasts eight seconds; pending Config tests remain informational, accepted results are success, cancellation is unconfirmed warning, failures stay error, and completed non-failed results dim after four seconds and expire after seven. Fresh messages never default to muted styling. Text continues to explain the state without color.

Declared RGB contrast against the slate footer is approximately 7.9:1 for information/hotkeys, 6.6:1 for success, 5.6:1 for warning, 4.8:1 for error, and 5.4:1 for hint labels/separators. The default palette guards active footer roles at 4.5:1 or more and fresh information at 7:1 or more using sRGB relative luminance; deliberate dimming remains approximately 3.4:1. Selected text/background is approximately 10.3:1. These measurements describe the declared pairs, not a guarantee for every terminal: limited-color profiles quantize colors, fonts/bold vary, and body contrast depends on the inherited terminal background. All body prose receives `Text`; a custom `Background` covers the complete viewport, including below-minimum fallback and dialog margins. Nested ANSI resets restore the enclosing surface defaults, retaining explicit swatch/selection/footer colors. Inspect TrueColor, ANSI256, and no-color behavior; color cannot replace labels or focus markers.

Printer-reported filament swatches remain a justified color exception: `filamentColor` validates reported RGB/RGBA data and renders its RGB swatch, while preserving the textual color/unknown label. Do not remap reported material colors to a theme's accent. App-owned RGB literals belong in the JSON palette definitions; tests may use independent synthetic palettes/telemetry colors. The loader validates the schema and RGB syntax without adjusting user colors or enforcing contrast. The Gruvbox Dark example supplies all roles and an explicit dark body background. Hotdog demonstrates a very light cream body, dark text, red accents/borders/status bar, and a yellow selection. C64 uses a deep blue body, light blue/lavender text and borders, blue selections, and a darker blue footer, with brighter feedback colors. IBM 3270 uses a near-black green body, green text and borders, reverse green selections, and a dark green footer. Its app-owned colors stay green; state labels and emphasis retain meaning, and reported filament swatches remain telemetry. DeskMate follows the DeskMate II-style blue/light-gray/dark-gray/black text-mode scheme, with a blue body, gray selection, and gray footer; labels and weight preserve message meaning. Bundled selected text/background pairs and active footer roles are guarded at 4.5:1 or more, fresh information at 7:1 or more, and Hotdog/C64/IBM 3270 body roles and selected text/background pairs at 4.5:1 or more against their declared backgrounds. Preserve text meaning and inspect custom themes in TrueColor, ANSI256, and no-color profiles.

## Interaction and layout contracts

- Reuse key meanings from `internal/ui/keys.go`. Keep dashboard help, dialog hints, and the [keyboard reference](../user/usage.md#keyboard-and-navigation) consistent with actual routing. Context-specific reuse is allowed when the active dialog makes the action clear.
- About (`A` from the dashboard) is read-only and owned by the shared dialog router. Show app name/version, platform, project URL, branding, and attribution without field labels, followed by the effective theme source rather than saved preferences. Render “Theme:” and “Theme Palette:” in secondary text, with the theme source in primary text, consistent with dashboard field labels and values. Do not display or collect login email for About. Under “Theme Palette,” show an unlabeled grid of unique explicit RGB colors sorted by hue, with achromatic colors first from dark to light and saturation/value tie breakers. Omit inherited terminal colors whose RGB is unknown. This user-requested presentation is an exception to palette role/value labels: no-color mode retains solid swatch shapes without identifying colors; documented theme files remain the role/value reference. Adapt columns to available width. Preserve focus/selection on Enter/Escape return, scroll through status inspection and below-minimum restoration, and ongoing telemetry. Wrap long theme paths without clipping the project URL.
- Help has its own scrollable keyboard reference and close hints; dashboard shortcuts remain captured until it closes. `Ctrl+E` opens read-only status details from the dashboard or a dialog, preserving the suspended owner, selection, input, confirmation, and scroll. Escape or `Ctrl+E` returns; quitting stays dashboard-only. Compact shutdown retains its own controls and does not open status.
- Give one dialog explicit ownership through `dialogState` and `routeFor`. Keep input, rendering, synchronization, cleanup, and any suspended parent consistent. Telemetry and asynchronous results continue during dialogs; automatic attention waits for the current owner to finish.
- Keep Escape's close/return behavior and the existing dashboard-only quit behavior. Confirm destructive local bulk actions, preserve newly arriving occurrences during confirmations, and keep local notice decisions distinct from printer-side actions.
- Support the minimum 60 × 18 terminal. Below that size, hidden navigation, mutations, exports, and confirmations stay blocked; Escape, dashboard quit, and compact shutdown controls retain their documented behavior. Resizing back restores dialog state. Keep details/notices stacked below 105 columns and side by side at wider sizes unless a requested change deliberately revises this contract.
- Restore the saved farm filter/sort from the active configuration; F/S saves changes and dashboard `0` resets All printers / Name sorting, including from empty results. Keep dialog ownership and below-minimum guards, and reuse Config save failure/retry/shutdown behavior.
- Preserve selection by printer/notice identity through live updates, sorting, and filtering. Preserve focus and scroll where the selected identity remains; provide a defined fallback when it disappears. Show useful empty, disconnected, stale, unknown, saving, and failed-save states.
- The separate Config dialog (`,`) exposes General, Alerts, Printers, and Web Server sections using Tab/Shift+Tab, with arrow navigation and scrolling to keep the selected row visible. It edits all alert defaults and On/Off/Inherit printer overrides immediately, confirms reset-to-global, validates percentage input, and labels region changes as restart/login requirements. The low-filament threshold reconciles reported estimates immediately; the running account/region remains unchanged. It saves asynchronously to the launch configuration path. Preserve per-printer overrides, silent background saves, visible red failure/retry states, and shutdown tracking. Its explicit Test Notification action remains responsive, uses the global sound preference, shows pending/accepted/failed states, and cancels on close without consuming live notification identities. Config uses its single-row footer for selected-option helper text plus test feedback separated by a dot. Accepted feedback is prominent green, dims after four seconds, and expires after seven; test failures stay red. Shorten ordinary helper text before clipping result text at narrow widths. During percentage editing or reset confirmation, reserve the footer for apply/reset/cancel instructions; retain test feedback in Status / Feedback and restore it after editing if still current. Header hints follow the active edit/confirmation state. Show storage failures and retry guidance in its body; emphasize navigation/activation/close keys below its header.
- Web Server in Config toggles a default-off, session-owned loopback HTTP listener asynchronously. Its Port row defaults to 8080, accepts 1–65535 using arrows or validated typed input, and applies changes immediately through the same serialized lifecycle. An occupied port leaves the server stopped with an error and no fallback; retry requires an explicit action. Show Starting/Running/Stopping/Failed/Stopped explicitly and the complete `http://127.0.0.1:<port>` URL only after binding. Keep failure/retry guidance in Status / Feedback. Closing Config preserves the running listener; disabling and CLI exit stop it. Browser views use decorative local model sprites as described in [branding](../reference/branding.md#printer-sprites), with a generic fallback for unknown models; artwork never establishes telemetry. Browser views use the shared farm interpretation and allow explicit per-occurrence local hiding through the authoritative reducer, and distinguish unknown/last-known telemetry, local reviews, and physical resolution. Preserve keyboard/selection/scroll and below-minimum guards; server results and telemetry still update during dialogs.
- Desktop delivery is independently opt-in and must honor current categories, reviews, and snoozes while telemetry remains responsive in all dialogs. Show acceptance separately from visual delivery, preserve a failure indication and access to full details in the footer, and expose session counters in the existing alert dialog and bounded recent decisions in the dashboard’s `N` activity dialog. Keep selected activity stable through updates, show per-incident outcome/reason and grouped-request membership, and distinguish Accepted, Failed, Unconfirmed, Suppressed, and Paused in text as well as color. History is session-only; opening an empty activity view must not opt in to delivery. Expose Owner/Standby/muted-observer/paused states in text, and use `r` only to recheck an idle paused/standby worker with fresh telemetry and policy. Recovery must not reset identities or retry consumed attempts, and hidden recovery remains blocked below minimum size. Shutdown pauses/cancels delivery; canceling shutdown can resume it.
- Do not infer completion, resolution, runout, or connectivity from missing fields, elapsed time, color, or severity alone. Reuse the farm's interpretation and the distinctions documented in the user guides.

The full-screen action-needed dialog emphasizes printer/state and fault summaries, with intervention guidance immediately below each fault. Keep per-occurrence review status, code, and first app-observed timestamp secondary, with absolute local time/timezone/UTC offset and a tick-updated relative age. Label unavailable/future observations explicitly. Preserve independent notice identities, timestamps, focus, and scroll, including replaced occurrences. Keep full troubleshooting URLs accessible through inspection and browser actions. Keep acknowledgement, hide, snooze, and close in the single-row footer, with navigation below the heading; explain local decisions and physical intervention in the scrollable body.

Browser notice hiding must say it is a local decision and preserve acknowledgement, snooze, restoration, and physical fault resolution as separate concepts. Hide dismissed conditions in the browser inspector by default, with a counted “View hidden messages” / “Hide hidden messages” toggle to inspect them without changing notice decisions. Preserve this display choice and toggle focus through polling, reset the choice when opening a printer, and distinguish an all-hidden view from no reported conditions. Keep failed-save retry available when viewing hidden messages, label pending/applied separately from saving/saved/session-only/failed storage, and provide explicit save retry. Use session occurrence targets, reject stale/replaced targets, and keep active/suspended TUI views and browser tabs synchronized without losing selection/scroll. Preserve browser keyboard focus through polling and move focus to Close if a condition action disappears. Browser writes require the localhost request protections documented in architecture; local clients remain trusted.

Browser system notifications live in the Settings dialog, opened by an accessible gear button beside Help in the dashboard header. Keep notification controls out of the main farm area. Closing Settings with its close button or Escape restores focus to the gear and leaves automatic delivery running. Notification clicks close Settings before opening the matching printer. Browser system notifications have explicit Enable/Test/Disable controls, separate automatic opt-in and permission states, and readable capability/submission errors without interrupting monitoring. Request permission only from a user click. Keep controls and status keyboard-accessible and reflowing at narrow widths/200% text. Permission alone never enables automatic delivery. Establish a baseline on enable/reload/reconnect/long suspension; hidden enabled pages poll best-effort, while suspended/closed pages have no background guarantee. Notification clicks return to the matching printer/conditions; closing never changes local decisions. Show browser acceptance as unconfirmed presentation/sound. Go owns candidate identity and policy; the browser never infers completion from displayed telemetry. Browser claims are separate from native delivery and shared across connected browsers. See [policy and limits](../user/alerts.md#browser-system-notifications).

## Foreground serve presentation

`serve` and `serve --demo` have a compact colored status screen separate from the interactive farm dashboard. Keep the localhost URL first, cloud/demo mode, explicit HTTP and monitoring connection states, session uptime, bounded recent fixed-text diagnostics, persistent storage warnings, HTTP client activity, and `Ctrl+C to stop`. Reuse the default semantic palette for URL/headings, green healthy/connected states, amber connecting/reconnecting/warnings, red authentication/server/storage failures, and secondary metadata. Honor `NO_COLOR`, reduced-color profiles, and plain output; text remains authoritative. Connection does not establish fresh printer telemetry. Reflow to terminal width, reserve shutdown guidance before optional rows, and prioritize the URL on extremely short screens; the dashboard's 60 × 18 navigation minimum does not apply to this display. Inspect 120 × 40, 80 × 24, 60 × 18, 40 × 12, and 20 × 10, plus extreme-size wrapping guards.

Render at most once per second during monitoring. Keep at most three recent diagnostics and exclude external strings, payloads, account/printer identifiers, credentials, paths, and backend errors. Use plain changed-state logs when input/output is noninteractive or `TERM=dumb`; omit uptime-only log lines. The alternate screen and hidden cursor must restore on every exit; retain canonical terminal input and CLI signal ownership, without a second terminal reader. Show stopping before bounded persistence/monitor shutdown and preserve failure exit status. Serve uses the default palette independently of dashboard theme configuration and native notification delivery. Its HTTP ledger may show socket IPs and sanitized, bounded first-request user agents as an explicit display exception to fixed diagnostics. Group parallel/replacement sockets by IP and sanitized first-request user agent; ignore sockets with no request and use a five-second grace after the last socket closes. Label groups as best-effort HTTP clients rather than authenticated people/tabs, retain 32 events and at most 128 socket/group records, show tracking omissions, and truncate ledger rows within viewport width. Keep the ledger session-only and out of browser snapshots.

## Browser dashboard readability

Keep browser cards keyed by printer identity through monitoring updates. Patch changing telemetry and accessible labels in place; preserve connected image elements and unchanged source attributes so lazy/async-decoded sprites do not restart on each poll. Filtering, ordering, discovery/removal, and model-image/fallback changes must still reconcile correctly while retaining keyboard focus where the printer remains visible.

Use one inherited modern console-style font stack throughout the dashboard, including headings, metadata, numeric readings, form controls, and dialogs. The local system-monospace stack includes SF Mono/Menlo/Monaco, Consolas, and DejaVu Sans Mono, with a generic monospace fallback; do not introduce a separate serif family through font shorthands. Font assets must not require a CDN request.

At a default 16px browser root, keep body/primary readings at 16px and metadata/control labels at least 14px. Use relative font sizes and comfortable line height so browser text preferences can enlarge them. Let cards, metric columns, filters, and controls reflow instead of shrinking text to fit; check narrow viewports and 200% text enlargement without horizontal scrolling or clipped dialogs. Preserve readable unknown/last-known labels, visible keyboard focus, font-independent close icons, and reduced-motion preferences. Artwork remains decorative.

## Verification for a UI change

Extend the relevant behavioral tests when changing an interaction contract. Prefer semantic assertions, ANSI-aware bounds, synthetic telemetry, and explicit synchronization over full-frame snapshots or sleeps. Existing examples include `internal/ui/dialogs_test.go`, `modal_keys_test.go`, `resize_input_test.go`, `overview_test.go`, `offline_test.go`, and the [PTY suite](terminal-tests.md). `make test` runs these with the race detector in Linux/macOS CI.

For layout or styling changes, inspect the affected states in `make demo` at 60 × 18, below minimum size, and a wide size such as 120 × 32. Check selected/unselected rows, empty/unavailable data, dialogs, text without color, clipping, and focus/scroll after updates as applicable. Automated tests cannot establish visual quality in every terminal. Report which states/sizes were actually inspected and which remain unverified; do not claim a demo or synthetic fixture establishes real-printer behavior.

Existing automated guards make the interaction contracts verifiable:

| Contract | Regression coverage |
| --- | --- |
| Dialog ownership, return paths, and deferred attention | `internal/ui/dialogs_test.go`, `modal_keys_test.go` |
| Block hidden actions below minimum size; continue telemetry/saves | `internal/ui/resize_input_test.go` |
| Stable selection, filters/sorts, empty states, and bounds | `internal/ui/overview_test.go` |
| Offline text/color and selection across table widths | `internal/ui/offline_test.go` |
| Raw keyboard input, resizing, quit/signals, terminal restoration | `cmd/bambu-tui/pty_test.go` |

Keep these guards passing and extend them for new behavior rather than weakening assertions to fit a regression. Run `go test -race ./internal/ui ./cmd/bambu-tui` for the UI/terminal suites, or `make test` for all packages. Visual review and documentation impact remain required even when automated tests pass.

In the PR, describe the operator-visible before/after behavior, identify the contracts affected, link updated user guidance, and report regression tests and visual inspection results. An intentional departure from these defaults should be backed by the user's requested behavior, reflected in the direction/user guides, and covered by the relevant checks in the same change. Routine fixes within this direction do not need a separate approval step.
