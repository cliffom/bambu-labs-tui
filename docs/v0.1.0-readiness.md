# v0.1.0 readiness assessment

## Recommendation

The feature scope warrants **v0.1.0 once #10 is merged**. The planned daily-farm-usability work is covered: operators can manage saved reviews, locate troubled printers/upcoming completions, control interruptions, and export a local troubleshooting artifact. No additional feature is needed for that milestone.

Before publishing the final v0.1.0 tag, complete and record the targeted operational smoke checks in [#6](https://github.com/cliffom/bambu-tui/issues/6) and the [validation record](validation.md). That issue remains open. Current live evidence confirms displayed telemetry on H2D and X2D and a successful disposable native credential probe; it does not establish real-account restart, reconnect, review persistence, alert/snooze, or firmware behavior. Automated and demo coverage cannot replace that evidence.

## Remaining release evidence

Record actual host OS, printer models/firmware, test date, and results rather than inferring them from synthetic fixtures:

- [ ] Save a real email-code session, restart without another login, and verify logout.
- [ ] Reconnect the monitor after a temporary network interruption and confirm fresh status.
- [ ] Observe naturally occurring pause/recovery/completion and compare firmware/telemetry with Bambu's applications.
- [ ] Verify acknowledgements/dismissals survive restart and an observed resolution/recurrence returns unreviewed.
- [ ] Verify action-needed prompts and per-printer snooze/resume/restart behavior while telemetry continues; check that recovery/maintenance do not interrupt.
- [ ] Check farm filtering/sorting and inspect a local diagnostic artifact on the supported live setup before voluntarily sharing any data.

Do not deliberately fault a printer to satisfy a checklist. Record unavailable scenarios as untested with a clear limitation. Keep #6 and the validation record authoritative for hardware results.

## Release preparation

This branch leaves `VERSION` at the released base and records diagnostics as **Unreleased**. When the final release decision is made, update version metadata, installation examples, and the changelog together, then follow [publishing](publishing.md). The feature PR does not tag or publish a release.
